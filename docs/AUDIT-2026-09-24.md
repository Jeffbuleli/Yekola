# Audit Yekola - 24 septembre 2026

**Périmètre :** dépôt `/Users/mac/Documents/Yekola`, production `https://yekola.mcbuleli.com`, VPS `162.35.181.98` (`/opt/yekola`).

**Référence réutilisation :** monorepo McBuleliP2P (patterns HTTP/API uniquement, pas de fork).

## 1. Verdict exécutif

Yekola est aujourd'hui un **site marketing statique crédible** (landing ~747 lignes, ton Ansella-like, pricing Pilot/École/Réseau, FAQ) déployé en HTTPS sur le VPS principal McBuleli, avec un **brief produit solide** et une **chaîne ops rsync + nginx + certbot** fonctionnelle. En revanche, **aucune des promesses pédagogiques ou SaaS du pitch n'est implémentée** : pas d'application Next.js, pas de base de données, pas d'authentification, pas de parcours, pas de PWA offline, pas de quiz, pas de Meet intégré, pas de MoMo, pas de badges. Le jury verra une **vision documentée + landing**, pas une école virtuelle. Le décalage marketing/produit est le **risque n°1** (crédibilité). Le dépôt Git est **local seulement** (push GitHub bloqué), ce qui fragilise backup, CI et collaboration hackathon. Priorité absolue avant démo : **une app minimale** (auth + 1 parcours démo + 1 quiz + sync simulée ou réelle + lien Meet JWT + écran formateur) plutôt que d'enrichir encore la landing.

## 3. Recommandation stack

**Cible : Next.js 15 (App Router) + TypeScript + Tailwind CSS + Drizzle ORM + Postgres en prod (+ SQLite option dev local).**

| Choix | Pourquoi |
|-------|----------|
| **Next.js 15 App Router** | Même famille que McBuleliP2P : Server Actions, routes API webhooks (PawaPay), déploiement Docker derrière nginx `127.0.0.1:3015`, SSR pour SEO pages centre + shell app authentifiée |
| **TypeScript** | Contrats stricts tenant/parcours/sync - réduit bugs jury sous pression |
| **Tailwind** | Vitesse UI « classe / parcours » moderne ; réutiliser tokens Yekola (`--yk-*`) |
| **Drizzle + Postgres** | Postgres déjà sur VPS principal ; migrations versionnées ; modèle multi-tenant propre (tables `tenants`, `users`, `enrollments`, `sync_events`) |
| **SQLite en dev** | Hackathon sans Docker Postgres local : `DATABASE_URL=file:./local.db` |
| **PWA (Serwist ou `@ducanh2912/next-pwa`)** | Preuve offline : manifest, SW, cache pack statique + API read-through ; aligné promesse « sans Internet » |
| **Pas de fork McBuleliP2P** | Copier **modules** (`src/lib/pawapay/*`, helpers Open Badge, client OpenAI) dans Yekola ou package interne minimal |

**Anti-patterns à éviter pour la démo :** Moodle embarqué, Electron, sync USB hub (P2), marketplace créateurs, SCORM.

## 6. Limites honnêtes

- **Offline « Kolibri-grade »** (gros médias, sync conflict robuste, hub USB) **n'est pas réaliste** en quelques jours : viser **pack léger + quiz/TP en queue** et assumer la limite en pitch.
- **Multi-tenant SaaS complet** (isolation forte, facturation, quotas) dépasse un MVP hackathon : **un tenant démo + flags** suffisent si on ne ment pas sur l'échelle.
- **MoMo production** dépend KYC/opérateurs/délais PawaPay : sandbox ou **« paiement enregistré, activation manuelle »** est acceptable si annoncé.
- **Meet** reste **dépendant** de l'infra McBuleli (JWT, VPS Jitsi) : panne live = plan B enregistrement audio ou visio externe.
- **GitHub bloqué** : risque perte machine unique ; mitiger export bundle + remote alternatif urgent.
- **Contenu pédagogique** : sans partenaire TVET, le parcours démo reste **générique** - OK pour jury tech, faible pour jury métier.
- **Sécurité** : MVP auth simple ; pas audit pentest.
- **Accessibilité réseau RDC** : tester sur **vrai 3G/throttle** ; le landing actuel est lourd (images PNG logo ~270 Ko).
